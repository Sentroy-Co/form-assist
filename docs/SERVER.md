# Server and credential management

`@sentroy-co/form-assist/server` exposes `createAssistantServer`. Register authoritative form snapshots and connections as `{ provider, models: ['explicit-model-id'] }`, and provide both `getContext(request)` and `authorize(context, action, resource)`. The host derives a nonempty `tenantId` from its authenticated session; never derive it from request JSON. Authorize both form and connection resources for `propose`. Mount `handle` behind the host's authentication and CSRF/origin policy. The client supplies current values and revision, not a schema or provider credential. The host must ensure the caller may access those values. Provide `resolveForm(formId, context)` for tenant-specific authoritative values and revision; the handler checks revision and retains the registered schema and field policies. Without this callback the static registration accepts the browser revision, so the host must enforce any server-side revision check itself. Client values may contain only registered writable paths; protected and unlisted values are rejected, while protected values come from the authoritative snapshot.

POST a protocol v1 `ProposeRequest`. JSON returns a validated plan. `Accept: application/x-ndjson` returns a single complete `result` event after validation; it does not expose partial provider output. Errors return a generic redacted JSON error. Defaults limit body/output to 256 KB, 200 fields, 30 seconds, 10 concurrent and 60 requests per minute per tenant, and input/output byte ceilings (named `maxInputTokens` and `maxOutputTokens`) to 32,000/8,000, and checks provider-reported usage against those same limits. Configure limits for deployment; byte ceilings are conservative proxies rather than guaranteed token counts, and usage is checked only when reported, so these limits cannot guarantee provider billing. Rate and concurrency counters are process-local; distributed deployments need a shared host-level limiter. Provider calls receive an abort signal; an adapter must honor it to actually stop remote work.

`createCredentialManager` provides an authenticated management handler: GET at its mount path lists masked summaries; PUT `/:id` creates or updates, DELETE `/:id` removes, and POST `/:id/test` with `{ "allowPaidTest": true }` invokes the optional host-supplied test callback. Testing can incur provider charges. Each route requires the corresponding `credentials:list`, `credentials:write`, `credentials:delete` or `credentials:test` authorization. Mount and route paths consistently, use HTTPS and CSRF protection, and restrict access to administrators. A PUT requires name, provider, model, enabled, default and secrets; omit secrets on update to preserve existing values. Read responses never include secret values. An error from a store or test is replaced with a generic response. Avoid logging request bodies or store records.

`createMemoryCredentialStore()` is ephemeral. `createEnvironmentCredentialStore(mapping, env)` is read-only and resolves host-provided environment variables. `@sentroy-co/form-assist/server/node` exports `createEncryptedFileCredentialStore({directory, activeKeyId, keys})`. Keys are 32-byte AES-256-GCM keys kept outside the storage directory. Files are tenant scoped, authenticated with tenant and record ID, and replaced atomically. Back up keys separately. For rotation, supply old and new keys, choose the new active ID, then read and rewrite every record for each tenant; only remove old keys after migration and backups are accounted for. Loss of a key makes its records unreadable. File permissions depend on the host filesystem; shared/multi-process deployments should use an appropriate managed secret store. Implement `CredentialStore` for a secret manager.

API keys are distinct from chat subscriptions: [Google AI Studio](https://ai.google.dev/gemini-api/docs/api-key), [Claude](https://platform.claude.com/docs/en/get-api-key), [OpenAI](https://developers.openai.com/api/reference/overview).
